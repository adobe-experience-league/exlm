Trade-offs for Mixed Events Source

Ticket: EXLM-6102 (Events V2 Post-MVP)

Author: Nitin Rachabathuni (Core Eng)

Branch / baseline: EXLM-6102 off main @ 56cafd76

Preview (all-Coveo baseline): Events Hub · Site search

Decision asked: Should ACS move forward with Upcoming from CDN/JSON and On-Demand from Coveo?

1. What we were asked

PdM / Core want a clear read on the trade-offs if ACS starts treating the two event families as two different backends:

  • Upcoming Events → CDN JSON (https://cdn.experienceleague.adobe.com/thumb/upcoming-events.json)
  • On-Demand Events → Coveo (same Search Hub we already use everywhere else)

The analysis has to cover Events Hub, regular Search, and the rest of the site — not just the Events page in isolation.

This page is the go / no-go write-up. It is not an implementation plan.

2. Executive recommendation

Recommendation

Do not move ACS (or EXLM consumers) to a mixed Upcoming=CDN / On-Demand=Coveo model as the long-term architecture.

Keep Coveo as the single source of truth for both Upcoming (Event|Upcoming Event) and On-Demand (Event|On Demand Event) on Events Hub, site search, browse, and V2 card rails.

Keep the CDN JSON feed only as a legacy / transitional path for blocks that still call the old upcoming-event key — and plan to finish migrating those rails off it. Do not re-expand CDN as the Upcoming source of truth.

Conditional exception (only if PdM insists on promo-window UX that Coveo cannot express today): CDN may remain a secondary feed for a small “live now / promo window” strip, while Hub + Search continue to read Upcoming from Coveo. That is a deliberate dual-write / dual-read cost, not a simplification.

Why in one line: Events Hub already merges Upcoming + On-Demand in one Headless engine (facets, counts, pagination, keyword, Tab analytics). Splitting Upcoming out of Coveo undoes that work and creates three different truths across Hub, Search, and card rails.

3. How things work today (code reality)

EXLM already has two Upcoming paths. Events V2 deliberately moved the important ones onto Coveo. The mixed model ACS is asking about would reverse that on purpose.

3.2 The two backends in plain language

  • CDN JSON — static file, ~11 Upcoming events today (~17 KB), CORS *, sessionStorage cache key liveEvents. Schema is now version 3: promoStartTime / promoEndTime / eventStartTime, series, location, speakers, roles, skill levels, CTA, image. No keyword search, no facets, no server pagination, no On-Demand.
  • Coveo — indexed Event|Upcoming Event and Event|On Demand Event. Shared Search Hub Experience League Learning Hub. Events Hub adds Tab Events Hub. Stale Upcoming is filtered with el_event_start_time >= now (not @date — that field is index/batch time for Upcoming and will wipe the catalog if misused).

3.3 Important drift already in the repo

The live CDN file is v3 (eventStartTime, promo window). The EXLM JSON adaptor (browse-cards-upcoming-events-adaptor.js) and the legacy upcoming-event product filter still expect legacy fields (startTime / endTime / time).

Against today’s feed, that adaptor’s “is this event live?” check never matches — so legacy CDN rails are already out of sync with the published JSON. That alone is a warning against making CDN the forward path for Upcoming without a deliberate schema contract and adaptor rewrite.

Coveo V2 rails do not have that problem; they read el_event_start_time from the index.

4. Use cases we walked

# Use case Mixed CDN+Coveo impact All-Coveo (current V2)
1 Events Hub default view (both types, no keyword) Must merge CDN Upcoming + Coveo On-Demand client-side. Facet counts, result totals, and pagination stop being trustworthy from a single Search response. One Headless query. Client already regroups Upcoming-then-On-Demand for Date in mixed mode.
2 Hub — Upcoming only + Date sort CDN sort in the browser. Product/Series facets either empty for Upcoming or need a second, non-Coveo filter pass. Coveo field sort on el_event_start_time ascending.
3 Hub — On-Demand only + Popularity / Date Still Coveo (fine). Same.
4 Hub — keyword across both types Keyword hits On-Demand in Coveo only unless ACS also builds search over JSON. Upcoming silently missing from keyword results. One q across both types.
5 Hub — Product / Series facets Facet values from Coveo omit Upcoming that only exist on CDN → wrong counts, missing checkboxes, “filter returns nothing” bugs. Facets reflect the same index as results.
6 Hub — pagination Page size over a merged list is hand-rolled; easy to desync with Coveo pager state. Native Headless pager.
7 Site search — discover Upcoming If Upcoming leaves the index (or goes stale while CDN is fresh), /search and Content Type Event|Upcoming Event lie relative to the Hub. If Upcoming stays in Coveo and comes from CDN on Hub, users see two catalogs. One catalog; stale Upcoming stripped via shared aq helper.
8 Browse All / product browse with Events filters Same dual-source pain as Hub if browse is told to mix. Headless + isEventsV2 hierarchical types.
9 Homepage / article card rails (Upcoming) Possible to keep CDN for a small rail — but then rail ≠ Hub ≠ Search. upcoming-event-v2 already on Coveo.
10 Promo window (“show only while promo is live”) CDN wins today — promo start/end are first-class on JSON v3. Coveo path filters on event start, not promo window. Needs either a Coveo field for promo window or a small CDN-only promo strip.
11 Register CTA / location / speakers on Upcoming cards Present on JSON v3; must be mapped 1:1 into Coveo fields for parity if Coveo stays SoT. Already mapped for V2 cards from index fields.
12 Analytics (Events Hub Tab, UA originLevel2) CDN-sourced Upcoming never participates in Search API / Headless analytics the way Coveo results do. Mixed lists muddy “what did we search?” Tab Events Hub lines up with Search Hub for ML.
13 Failure modes CDN 404 → empty Upcoming half; Coveo 419 → empty On-Demand half; UI looks “half broken.” One failure domain; token renew path already exists.
14 Locales CDN feed is effectively a single catalog. Coveo requests carry locale. Better fit for localized Hub/Search.
15 Deep links / share URLs Hub hash assumes Coveo facet values (f-el_contenttype=Event|…). CDN-only Upcoming cannot round-trip through that model cleanly. Hash ↔ Headless UrlManager already wired.

5. Trade-off summary

5.1 What mixed gains

  • Promo-window semantics that already exist on JSON v3 without waiting on a Coveo field + reindex.
  • Potentially faster “we just published an Upcoming” visibility on CDN (blob overwrite) vs waiting for crawl/index — if publish ops are tighter on the blob than on the index.
  • Slightly less Coveo traffic for Upcoming-only legacy rails (small catalog anyway).
  • Familiarity for anyone still operating the thumb JSON pipeline.

5.2 What mixed costs (the real bill)

  • Events Hub becomes a federation layer. We already paid for unified Headless (Tab, aq, facets, sort contexts, client regroup for mixed Date). Mixed source reopens merge, count, and pagination debt.
  • Search and Hub diverge unless Upcoming remains fully indexed and kept in lockstep with CDN — which means ACS still dual-writes, so mixed read does not remove publish complexity.
  • Facet and keyword integrity break for Upcoming the moment it leaves the index used by Hub filters.
  • Schema tax forever: CDN v3 vs Coveo raw fields vs browse-card model. We already see adaptor drift on the legacy path.
  • Analytics and ML see an incomplete Events story when half the Hub list never hit Search API.
  • QA matrix doubles: every Hub case (upcoming-only / on-demand-only / mixed × sorts × facets) needs a CDN+Coveo variant.
  • Ownership blur: who is right when CDN says “live” and Coveo says “stale” (or the reverse)?

6. Surface-by-surface call

Events Hub

Mixed is the highest cost surface. Sort is already contextual (Upcoming Date → el_event_start_time; On-Demand Date → date; mixed Date → relevance + client regroup; Popularity only when On-Demand-only). That design assumes one result set. Pulling Upcoming from CDN forces a second client merge on top of the merge we already do — and breaks facet counts.

Call: Hub stays all-Coveo.

Regular Search (/search)

Atomic already treats Upcoming as a normal content type with a stale guard shared with the rest of the site. Removing Upcoming from Coveo makes Search lie. Keeping Upcoming in Coveo while Hub reads CDN creates two catalogs.

Call: Search stays all-Coveo; do not special-case Upcoming onto CDN.

Other site parts

  • Migrate upcoming-event and events-cards off the legacy JSON key onto Event|Upcoming Event (same path as upcoming-event-v2).
  • Recs / featured / tabbed: keep authored V2 types on Coveo.
  • Topic “event” tab: leave as-is unless a separate ticket wants V2 types there.
  • CDN JSON: keep publishing for now if external consumers exist, but EXLM product UI should not grow new dependencies on it.

7. Ops, freshness, ownership

Topic CDN JSON Coveo
Freshness Blob replace; Last-Modified on the object. Browser may hold sessionStorage for the tab session. Index lag after publish; mitigated by existing stale-Upcoming aq.
Catalog size Small (order of tens). On-Demand is large; Upcoming small.
Failure Empty Upcoming rails / half-empty Hub if mixed. Token 419 renew; empty search.
Locale Single feed. Request locale.
Promo window Native (v3). Needs field + reindex or accept event-start semantics.
Who fixes “wrong event on Hub”? JSON publishers + whoever owns the blob. Index/content owners + Coveo field mapping.

If ACS dual-writes (CDN and Coveo) under option D, publish runbooks must say which system wins for Hub vs promo strip. Silent drift is how we got the v3 vs adaptor mismatch.

8. Decision for PdM and Core

Question Answer
Should ACS implement mixed Upcoming=CDN / On-Demand=Coveo as the forward architecture? No.
What should ACS do instead? Keep indexing both types into Coveo. Treat CDN as legacy/external. Align JSON schema + any remaining EXLM JSON consumers, or delete the consumers.
When is CDN still justified? Optional promo-window strip (option D), or non-EXLM consumers of the public JSON — not Hub/Search.
What EXLM follow-ups make sense after this spike? (1) Migrate upcoming-event / events-cards to V2 Coveo. (2) Either update the JSON adaptor to v3 or stop calling it. (3) If promo window is required on Hub cards, add Coveo fields — don’t split the Hub backend.

10. Open questions left for PdM (not blockers for the recommendation)

  1. Does any external consumer (outside EXLM) depend on upcoming-events.json staying public and v3-shaped?
  2. Is promo window (not event start) a hard requirement on Events Hub cards themselves, or only on a marketing strip?
  3. Are we willing to dual-write Upcoming to CDN and Coveo for a transition period while legacy rails die?

None of these change the core recommendation: do not make mixed read the architecture.
