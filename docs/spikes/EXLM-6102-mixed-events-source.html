Trade-offs for Mixed Events Source

Related ticket: EXLM-6102 · Events V2 Post-MVP

Owner: Nitin Rachabathuni

Last updated: 22 Oct 2026

Live references: Events Hub (production) · Site search (production) · Branch preview — Events Hub · Upcoming events JSON (CDN)

Summary

Experience League shows two kinds of events today: Upcoming (live or soon-to-happen sessions people register for) and On-Demand (recordings people watch later). Those two catalogs can be fed from different systems. The question on the table is whether we should deliberately run a mixed model: Upcoming from the public CDN JSON file, On-Demand from Coveo search.

Conclusion

We should not adopt mixed source as the long-term approach for Events Hub, site search, or the main event card experiences.

Both Upcoming and On-Demand should continue to come from Coveo wherever learners search, filter, or browse events together. The CDN JSON file remains useful only as a legacy or secondary feed (for example a small promo strip), not as the system of record for Upcoming.

That recommendation is about product consistency and operational cost, not about blocking a short-term experiment. The rest of this page explains what “mixed” would mean in practice, where it helps, and where it creates uneven learner experiences.

What “mixed source” means

Two backends already exist in the Experience League world:

CDN JSON Coveo
What it is A published file on the assets CDN (upcoming-events.json) The same search index that powers Events Hub, site search, and most card rails
What it holds today Upcoming events only (small set — on the order of tens) Both Upcoming and On-Demand (On-Demand is the large catalog)
Strengths Simple to publish; supports a clear promo window (when an event should appear / disappear in marketing terms) Search, filters, counts, sorting, pagination, shared analytics, and one catalog across the site
Limits No real search or facets; no On-Demand; one language-shaped catalog Depends on indexing; promo-window fields are not first-class the way they are on the JSON today

Mixed source would mean: the product reads Upcoming from the JSON file and On-Demand from Coveo, then stitches those results together in the UI (especially on Events Hub).

Where events show up today

This matters because a source change on one page quietly affects others if learners expect the same catalog everywhere.

Experience Upcoming On-Demand Why it matters for mixed source
Events Hub Coveo Coveo One list, shared filters (product, series, event type), keyword, and paging. This is where mixed source hurts most.
Site search Coveo Coveo Learners discover events alongside docs and other content. If Upcoming only lives on JSON, search either goes stale or shows a different set than the Hub.
Browse / product pages with event filters Coveo (Events V2) Coveo Same filter model as Hub. Mixed source would need the same merge logic again.
Upcoming event card rails (current Events V2 pattern) Coveo — Aligned with Hub and search.
Older Upcoming card rails still on JSON CDN JSON — Already a second path. The live JSON format has also moved ahead of what those older rails expect, so they are a weak foundation to build on.

On-Demand has never lived in the CDN file. Mixed source is not “two equal catalogs.” It is “Upcoming from file + On-Demand from search,” with the product responsible for combining them.

Trade-offs

Where mixed source helps

  • Promo windows. The JSON already knows when an Upcoming event should be promoted (start and end of the promo). Coveo filtering today is closer to “has the event started yet?” If marketing needs promo timing as a hard rule on a small strip, JSON is a natural fit.
  • Publish simplicity for a tiny Upcoming list. Replacing a file can feel faster and more direct than waiting on search indexing — when the only job is “show these few upcoming items.”
  • Familiarity. Teams that already maintain the thumb JSON keep a workflow they know.

Where mixed source costs us

  • Events Hub stops being one catalog. Filters, result counts, keyword search, and page numbers only stay honest when both event types come from the same system. Mixing sources means the Hub has to invent counts and pages after the fact. Learners will see wrong totals, missing filter options, or empty results that look like product bugs.
  • Keyword search becomes uneven. Typing in the Hub (or site search) can find On-Demand in Coveo while Upcoming from JSON never participates — unless we build a second search over the file. Upcoming quietly drops out of “search events.”
  • Hub and site search can disagree. Either Upcoming leaves Coveo (search lies relative to the Hub), or Upcoming stays in Coveo and also comes from JSON (two catalogs to keep in sync). Mixed read does not remove dual-publish work if we still care about search.
  • Sorting gets harder, not easier. The Hub already treats “Date” differently for Upcoming vs On-Demand, and when both types are visible it groups Upcoming first, then On-Demand. That only works cleanly on one result set. Two backends mean two sorts and a hand-built merge.
  • Shared links and filters. Bookmarks and deep links on the Hub assume Coveo-style event type filters. CDN-only Upcoming does not round-trip through that model cleanly.
  • Analytics. Events Hub search behavior is tied to Coveo. Upcoming loaded only from JSON never shows up the same way in that picture, so “what did people find on Events?” gets blurry.
  • Failure modes look half-broken. JSON outage → Upcoming missing. Coveo outage → On-Demand missing. The page can look fine for one type and empty for the other with no single explanation for support.
  • Two schemas forever. JSON fields, Coveo fields, and card display fields already drift (the published file format and older JSON consumers are out of step today). Mixed source locks that dual mapping in as a permanent cost.
  • Locales. Coveo requests carry language. The CDN feed is effectively one catalog. Mixed source makes localized Hub/search harder for Upcoming.

Options

Option Idea Learner experience Operations Verdict
A. Both on Coveo Keep Upcoming and On-Demand in search; finish moving leftover JSON rails onto the same path One catalog across Hub, search, and cards One publish → index path for product UI Recommended
B. Mixed read Upcoming from JSON, On-Demand from Coveo Hub/search risk inconsistency; filters and keyword degrade Merge logic + likely dual publish if search still matters Not recommended
C. Everything on JSON Grow the file into the full events platform Lose real search/facets for On-Demand unless rebuilt JSON becomes a CMS Out of scope / worse
D. Coveo everywhere + JSON promo strip Hub and search stay on Coveo; optional marketing strip still reads JSON promo windows Main experiences stay consistent; strip can differ on purpose Dual write only where promo timing is required Acceptable compromise if promo window is a hard requirement

Recommendation by surface

  • Events Hub — Stay on Coveo for both types. This is the highest-cost place to mix sources because filters, counts, keyword, and paging all assume one catalog.
  • Site search — Stay on Coveo. Upcoming should not be “Hub-only via JSON” if learners also search the site.
  • Card rails and browse — Prefer the same Coveo Upcoming/On-Demand types as the Hub. Retire older JSON-only rails over time rather than expanding them.
  • CDN JSON — Keep publishing if other consumers need the public file, or if we deliberately keep a promo strip (option D). Do not grow new primary product experiences on it.

Decision

Question Answer
Should ACS move forward with Upcoming from CDN and On-Demand from Coveo as the main architecture? No.
What should we do instead? Keep indexing both event types into Coveo. Treat the CDN file as legacy or secondary. Finish aligning leftover JSON consumers, or remove them.
When is the CDN file still justified? Optional promo-window strip (option D), or non–Experience League consumers of the public JSON — not as the system of record for Hub or site search.
Follow-ups worth scheduling after this decision Migrate remaining JSON-based Upcoming rails onto the Coveo Upcoming type; resolve JSON format drift for any consumer that must stay; if promo windows are required on Hub cards themselves, add that to Coveo rather than splitting Hub backends.

Open questions for product (do not block the recommendation)

  1. Does anyone outside Experience League depend on the public upcoming-events.json staying available in its current shape?
  2. Is promo window (not simply “event hasn’t started yet”) required on Events Hub cards themselves, or only on a marketing strip?
  3. Are we willing to dual-publish Upcoming to JSON and Coveo for a transition while older rails are retired?

None of these change the core call: do not make mixed read the architecture for Hub and search.
