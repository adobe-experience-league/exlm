# EXLM-5837 — Tab (`originLevel2`) for Events Hub

**Status:** Front-end change is on branch `EXLM-5837` for a preview. Library evidence is in `docs/spikes/EXLM-5837-evidence.json` (25 Sep 2026). Live Content Browser still needs a preview with a real Coveo token. Delivery ticket remains **EXLM-5812**. Do not upgrade Coveo packages.

**Clones:** EXLM-5812 (delivery story, same title).

## Thesis

Events Hub can send a dedicated Coveo Tab without a new Search Hub and without an Atomic upgrade. The search UI on `/events` is **Headless**, not the Atomic `atomic-search` block. `@coveo/headless@2.42.0` already exports `buildTab`. An active tab writes its `id` to the Search API `tab` parameter and to usage-analytics `originLevel2`.

Pass that id only from `events-search`. `browse-filters` calls the same engine helper and must stay untagged, or the new Tab leaks onto every browse page that shares `Experience League Learning Hub`.

| Ticket assumption                                     | Code (24 Sep 2026)                                                                                                                                                                                                                                        |
| ----------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Events Hub is an Atomic search interface              | `blocks/events-search/events-search.js` calls `initiateCoveoHeadlessSearch`                                                                                                                                                                               |
| Add `atomic-tab` because Atomic has no Tabs component | Atomic **3.13.0** (CDN in `scripts/load-atomic-search-scripts.js`) already ships `atomic-tab` and `atomic-tab-manager`. That block is site search (`blocks/atomic-search`), not Events Hub                                                                |
| `originLevel2` is unset everywhere                    | With no Tab, Headless still sends originLevel2 `default` (the library default). It does not send `Events Hub`. | Admin Console change is not enough                    | Correct. No request body in this repo sets `tab`                                                                                                                                                                                                          |

Search Hub stays shared. Tab is the narrower key.

## Recommended change (EXLM-5812)

Feature: Events Hub search. Blast radius: `scripts/coveo-headless/index.js` (shared with `blocks/browse-filters/browse-filters.js`) and `blocks/events-search/events-search.js`.

1. Add an optional `tabId` argument to `initiateCoveoHeadlessSearch`. When it is set, after `configureSearchHeadlessEngine` and before the first search:

```js
module.buildTab(searchEngine, {
  initialState: { isActive: true },
  options: { id: tabId, expression: '' },
});
```

2. `events-search` passes `tabId: 'Events Hub'`. Leave `expression` empty. The events result set already comes from `baseAdvancedQuery` (`BASE_COVEO_ADVANCED_QUERY_EVENTS`). A tab expression is ANDed into the query and would change results.
3. Do not pass `tabId` from `browse-filters`. Do not change `searchHub`. Do not change `generateMlParameters` (`originLevel2: 'default'` is the solution-suggest ML filter).
4. Do not add `<atomic-tab>` to `blocks/atomic-search`. That would tag site search as Events Hub.

`buildTab` does not render UI. Headless would also put `tab=Events%20Hub` in the URL hash. `visibleHash()` strips that param when `tabId` is set, the same way Events Hub already hides `aq`.

Empty expression means the tab does not add a constant query (`cq`). A live `/en/events` preview is still required before Content Browser or usage-analytics screenshots. This machine has no Coveo token for that page.

## Surfaces that must stay untagged

These also send Search Hub `Experience League Learning Hub` and must not grow a Tab in this story:

- `blocks/browse-filters` (docs/browse search)
- `blocks/atomic-search` (`search-hub` attribute on `atomic-search-interface`)
- REST card queries in `getExlPipelineDataSourceParams` (`scripts/data-service/coveo/coveo-exl-pipeline-helpers.js`) — no `tab` field today. Upcoming/on-demand rails and other browse cards use this path. They are not the Events Hub search interface. Leave them alone unless a later ticket wants rail queries under the same Tab.

## Pipeline / ranking / sort audit

Not in git. Coveo Admin Console only.

Do this after the front end is on a preview and Content Browser shows `tab=Events Hub` from `/en/events` only:

- Find query pipeline conditions, ranking expressions, and sort rules whose condition is only Search Hub = `Experience League Learning Hub` and whose intent is Events Hub.
- Add **Tab is `Events Hub`** to those conditions. Do not retarget a rule that is meant to apply to docs, community, or site search.
- The earlier sort-rule leak was a Search Hub condition with no narrower key. The fix is the extra Tab condition, not a new Search Hub.

Until that audit, shipping the Tab changes the label from `default` to `Events Hub`. Rules that key off Search Hub alone keep matching Events Hub. Rules that key off Tab `default` stop matching Events Hub. Check both before production.

## How to validate

On a preview, `?martech=off`:

1. `/en/events` — Search API body includes `"tab":"Events Hub"` and `"searchHub":"Experience League Learning Hub"`. Usage analytics search events from that interface use `originLevel2: "Events Hub"` and `originLevel1` equal to the Search Hub. Content Browser shows the same Tab.
2. A browse-filters page — same Search Hub, originLevel2 stays `default`, not `Events Hub`.
3. The address bar on `/en/events` does not gain `tab=Events%20Hub`.
4. Events results, sort, and filters unchanged (empty tab expression).
5. Solution query-suggest still sends `originLevel2: "default"` inside `mlParameters` when a solution key is present.
